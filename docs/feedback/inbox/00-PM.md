# PM-00 产品评审 · code-video-showcase v2.3.4

> 口径：只答「为谁做 / 凭什么留下 / 下一步砍什么」；不报 bug、不读源码、不跑测试与渲染。基线 `f67616d`（v2.3.4）。

### P-01 真实用户是「带 Agent 的开发者」，不是「小白创作者」
- 判断: 今天能独立走完「安装 → 出片」的只有一类人：已有 Agent，且机器上有 Node 20/22、Chrome、FFmpeg、Python 3.10 + numpy/scipy。T01 无技术创作者与 T02 品牌运营没有可用入口；仓库里可见的验收全部由作者自己完成。
- 证据: `SKILL.md:14`（兼容性清单）；`README.md:9-13`（安装动作是"发给你的 Agent"）；`CHANGELOG.md:6`（v2.3.4 标题「看画面看出来的」）；`CHANGELOG.md:18-22`（v2.3.3 用作者一句话当验收题）；`package.json` 54 个 scripts 含 6 个 `dev:*` 本地服务。
- 反直觉点: 路线图写「小白选两下出片」（`CLUSTER-PLAN.md:4`），但产品把"安装"外包给 Agent——真正的第一用户是 Agent，小白是 Agent 背后的人。
- 建议动作: 对外定位收窄为「Agent 的视频编译器」；本期验收名单移除 T01/T02，只留 T03/T04，直到出现非作者的第二次成片记录。
- confidence: 9

### P-02 北极星「二次修改率 ≥60%」不可测，代码只支持"改得起"、不支持"算得出"
- 判断: 指标要求「会话」「10 分钟内」「成功」三要素，但 CLI 与脚本面没有任何会话 ID、运行时间戳或成功事件落盘；`scripts/telemetry.mjs`（C7-05）不存在，缓存 JSON 只存帧数。用文件 mtime 反推也不行——`test:all` 本身就是一堆真实渲染，会把 CI 当用户。
- 证据: `CLUSTER-PLAN.md:17`、`:224`、`:326`；`test -f scripts/telemetry.mjs` → false；`DECISIONS.md:14`（缓存 `.json` 仅 frames）；`package.json` 的 `test:all` / `test:styles-render` 均含真实渲染。
- 反直觉点: 段哈希与缓存让"第二次修改"在工程上已经很便宜（`DECISIONS.md:13-15`），产品却不知道它发生过——能力已就绪，度量为零。
- 建议动作: 先落最小事件表 `out/.cvs/runs.jsonl`：`{ts, project, specHash, dirtySegments, exit, qaPass}`；指标改为「同一 project 10 分钟内出现第二条不同 specHash 且 exit=0」，先能算再谈 60%。
- confidence: 9

### P-03 两天跑完计划里 W2–W14 的功能面，纵向闭环被跳过
- 判断: M0（13 人日，W1–W2）随 v2.1 在基线当天交付；M2/M3 的批渲染、竖屏、API、黄金回归、品牌包、变体、动效档位在 v2.2–v2.3 两天内全部出现。被跳过的是三个"面对真实用户"的工件：C0-07 旧项目迁移、C7-05 匿名遥测、C7-06 的 Docker 形态。
- 证据: `CLUSTER-PLAN.md:15`（M0/M1/M2/M3 = W2/W6/W10/W14）、`:88`（C0 13d）；Changelog 版本行 v2.1→v2.3.4 全为 2026-11-11/12；`test -f scripts/migrate-brief.mjs scripts/telemetry.mjs` → 两者均 false；仓库无 `Dockerfile`。
- 反直觉点: 这不是"超前"，是偏科——能演示的横向功能全做了，要面对存量项目与真实数据的纵向闭环一个没做。
- 建议动作: 冻结新功能两周，只补 C0-07 + C7-05 + Dockerfile；把 M1 验收从"功能存在"改成"非作者用户在 10 分钟内完成一次改版"。
- confidence: 8

### P-04 最该砍：自建 GUI 层（5 个 app / 6 个本地 server）
- 判断: wizard、canvas、script、versions、review 五个 GUI 全部以 `npm run dev:*` 启动，没有 build/start/打包脚本；而实际分发方式是 `git clone` 进 skills 目录、由 Agent 读 `SKILL.md`。目标用户不会手动起 6 个本地 server，这层是替"想象中的小白"建的，不是替今天的用户建的。
- 证据: `package.json` scripts 含 `dev:api/dev:review/dev:wizard/dev:canvas/dev:script/dev:versions`，无 `build`/`start`/`package`；`README.md:9-13`（Agent Skill 分发）；`DECISIONS.md:115`（API 只监听回环、单机单操作者）；`CLUSTER-PLAN.md:15`（GUI 属 M1/M2）。
- 反直觉点: GUI 的存在感与目标用户打开浏览器的次数成反比——他们让 Agent 调 `cvs`，不会为改一版去起 dev server。
- 建议动作: 两周内把五个 app 标 experimental 并移出主测试矩阵；只保留 `cvs` CLI、`__inspect/__patch` 契约与 `server/api.mjs`，所有编辑回到 spec。
- confidence: 7

### P-05 只做一件事提升周留存：把「再来一版」做成一条命令
- 判断: 周留存 = 7 天内出现第二次成功成片；今天重开项目要记住 13 个 `cvs` 子命令、54 个 npm script 和 out 目录约定，第二次的认知成本≈第一次。代码已有段缓存与 plan/manifest，缺的是一个"从上次继续"的单一入口。
- 证据: `SKILL.md:35` 子命令表 `new|ref|lint|plan|build|variant|ingest|motion|wizard|canvas|script|versions|test`，无 `again/last/resume`；`package.json` 54 scripts；`CLUSTER-PLAN.md:17`；`DECISIONS.md:13-15`（段哈希 + 缓存）。
- 反直觉点: 留存不是靠"再加一个模板"，而是靠"第二次比第一次短一个数量级"——第一次可以慢，第二次必须像 `git commit`。
- 建议动作: 加 `cvs again --project <dir> --set look.theme=amber-noir --build`：读上次 spec+manifest，只重编译 dirty 段，结束打印「改了 3/9 段，省 47 秒」。
- confidence: 8
